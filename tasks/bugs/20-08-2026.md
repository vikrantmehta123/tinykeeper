# Task: Bugs Identified by Claude

1. Currently, the server handles exactly one request per connection. src/main.rs:38 reads a frame, dispatches, then the spawned task ends and the socket drops. There's no per-connection loop. Real ZooKeeper clients hold one long-lived connection and pipeline many requests — that's what xid is for. Related: there's no handshake. A real client's first bytes are a ConnectRequest (protocol version, last seen zxid, timeout, session id, password), not a RequestHeader, so today no genuine client can talk to this server at all. Fixed.

2. WAL order is not guaranteed to equal apply order — this is a real bug. At src/main.rs:75 you drop the WAL lock before taking the tree write lock. So client A can log Create /x, then client B logs Delete /x, and then B wins the race for the tree lock. The WAL says create-then-delete; the live tree saw delete-then-create. Replay after a crash produces a different state than the process had. The instinct to get fsync off the hot path was right, but the fix isn't releasing the lock — it's a single ordered commit pipeline (one task owns log-append and apply, in order) with group commit: batch N pending writes into one fsync. That's how you get both ordering and throughput, and it's also exactly the seam that Raft plugs into later: Fixed.

3. The WAL records attempts, not decisions. src/main.rs:63-79 logs the Create before tree.create() has been consulted. A create that fails with "Node already exists" is still durably written and fsynced. Replay papers over it only because src/wal.rs:66 uses let _ = to swallow the error. Two consequences: the log no longer means "these things happened," and any client can force unlimited fsyncs with invalid requests. Validate, then log, then apply: Fixed.

4. Malformed packets panic. buf.get_i32() panics when fewer than 4 bytes remain, and buf.split_at(path_len) panics when the length exceeds what's left. Worse, path_len comes from as usize on a signed i32 (src/protocol.rs:26) — a negative length becomes a gigantic usize. A 12-byte hostile packet is a remote-triggerable panic. Tokio catches it per-task so the server survives, but this is the kind of thing that should be Option/Result at every step.

5. The wire format doesn't match ZooKeeper's. Every response Stat is missing. Real GetDataResponse is data + Stat{czxid, mzxid, ctime, mtime, version, cversion, aversion, ephemeralOwner, dataLength, numChildren, pzxid}. And zxid is hardcoded to 0 everywhere. So even once the connection loop exists, a real client can't parse the replies. tasks/completeness-of-protocol.md covers this. Fixed.

6. set ignores the expected version, so there's no OCC. You wrote the right comment at src/storage.rs:79-82 — the version exists but nothing checks it. The client is supposed to send the version it read; you compare and return BADVERSION (-103) on mismatch. That comparison is optimistic concurrency control, and it's the primitive ClickHouse uses to avoid two replicas clobbering each other. Fixed.

7. create failure sends no reply at all (src/main.rs:96), so the client hangs — inconsistent with get/set/delete which do reply -101. delete silently removes whole subtrees (your comment at src/storage.rs:110-112 already flags this; ZooKeeper returns NOTEMPTY (-111)). And path validation is absent: //a and /a both resolve to the same node because src/storage.rs:13 filters empty segments, so one znode has multiple aliases. Fixed.
