# Task: Bugs Identified by Claude

1. `create_session` silently ignores WAL flush failure. At src/keeper_server.rs:129, `let _ = wal.flush().await` throws away the flush result after appending a `CreateSession` entry. The in-memory `session_state` was already mutated at line 120, so the returned `SessionId` behaves normally while the server runs. But if the flush actually failed, the WAL never got the entry durably. On restart, replay sees no `CreateSession` record for that id — the client's next request arrives with a session id the server has never heard of, and any ephemeral node the client thought it owned is not resurrected. Fix: propagate the flush error out of `create_session` (either `Result<SessionId, WalError>` returned to the connection handler which then sends `ErrorCode::SystemError`, or `.expect(...)` for v1 correctness at the cost of crash-on-disk-fail).

2. `close_session` silently ignores WAL flush failure and cleanup-delete failures. Same pattern in two places at src/keeper_server.rs:143 and :148. At line 143 the `CloseSession` WAL entry is flushed with the result discarded; the code then proceeds at line 146 to close the session and delete ephemerals in memory. If the flush failed, live state is closed but the WAL has no record — after a crash, replay resurrects the session and its ephemerals, so nodes the client believed deleted come back. The second silent failure is `let _ = tree.delete(path)` inside the cleanup loop: `session_state.close_session` on line 146 has already removed the path→session mapping, so if the delete fails (e.g. the node acquired children through another bug), nothing will ever try again — that ephemeral is leaked forever. Fix: propagate the flush error the same way as #1, and at minimum panic-or-loudly-log on the cleanup-delete failure since a leak here has no other recovery path.

3. Malformed packets still panic — the request parsers never got hardened, and the connection loop added two new panic sites. In src/protocol.rs every `from_bytes` calls `buf.get_i32()` on a buffer whose remaining length was never checked (`bytes::Buf::get_i32` panics when fewer than 4 bytes remain), and then does `let path_len = buf.get_i32() as usize` followed by `buf.split_at(path_len)`. `as usize` on a signed i32 turns a negative length into a gigantic value, and `split_at` panics when the index exceeds the slice. So a short or hostile frame is a remote-triggerable panic in `CreateRequest`, `GetDataRequest`, `SetDataRequest`, `DeleteRequest`, `GetChildrenRequest`, `ExistsRequest`, and `RequestHeader`. Two new sites make it worse: src/keeper_server.rs:188 does `RequestHeader::from_bytes(&mut buf).expect("unknown opcode")`, so any opcode outside the known set panics instead of replying `BadArguments`; and src/connection_handler.rs:110 reads `payload[4..8]` to peek at the opcode before anything has checked the frame length, so a 4-byte frame (which `read_frame` happily accepts — its guard is `0..=1_048_575`) panics before `apply`'s own `payload.len() < 8` check can run. Tokio contains each panic to one connection task, but a client can kill its own connection at will and every one of these is reachable pre-authentication. Fix: give `Buf` reads a remaining-length guard and return `Option`/`Result` at every step, reject negative lengths explicitly rather than casting, turn the unknown-opcode `expect` into a `BadArguments` reply, and move the opcode peek behind a length check.

4. `OpCode::Close` writes no WAL entry at all. src/keeper_server.rs:216-232 handles a client's explicit close by calling `session_state.close_session`, deleting the returned ephemeral paths, and clearing `watch_state` — all purely in memory. Nothing is appended to the WAL. The background-expiry path (`KeeperServer::close_session`) at least logs a `CloseSession` op, so the two ways a session can end have different durability. After a crash, replay sees the original `CreateSession` and no matching `CloseSession`, and resurrects a session the client explicitly closed along with every ephemeral node it owned — the same failure mode as #2, reached through a different door. The two paths should share one implementation that logs, flushes, then applies. Related: `KeeperServer::close_session` never calls `watch_state.clear(session_id)`, so an expired session's watch registrations are leaked in the tree even though its channel is gone.

5. Residual hole in the "validate, then log, then apply" fix (20-08 #3): `storage::create` can still fail *after* the WAL flush. `handle_create` pre-checks that the path is absent, the path splits, and the parent exists — but `KeeperStorage::create` has two rejection paths those checks don't cover: "Cannot create child under ephemeral node" (src/storage.rs:169) and the post-suffix `contains_key` collision check for sequential nodes (src/storage.rs:200, where the generated `/task-0000000005` may already exist even though `/task-` did not). In both cases src/keeper_server.rs:527 has already appended and fsynced the `Create` entry, and :544 then returns `BadArguments` to the client. The log now records an operation that never happened, and on the next restart `wal.replay` hits `.expect("WAL replay of Create failed: log is inconsistent with state")` at src/keeper_server.rs:72 — the server panics on startup and cannot recover without hand-editing the changelog. Fix: hoist both checks into `handle_create` before the append (compute the sequential path there so the collision check is done pre-log), or restructure so the append happens only once `create` has returned `Ok`.
